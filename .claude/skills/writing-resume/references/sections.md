# 이력서 항목별 기준

항목 작성·전체 검토에 사용한다. 사실·수치·본인 기여·충돌 판정은 공통 스킬 기준을 따르고, 이 문서는 항목과 압축·배치를 다룬다.

## 지원분야·제목

- 제출본에는 실제 공고의 기업명·직무명을 명확하게 표시한다. `기업명 직무명 지원_이름`을 제목에 쓰거나 이름 아래 `지원기업: … / 지원직무: …`를 둔다. 둘 다 반복할 필요는 없다.
- 마스터에는 기업별 정보가 미정이어도 된다. 제출본으로 전환할 때 해당 공고의 실제 명칭을 적용한다.

## 사진·인적사항

- 채용 연락을 받을 정확한 이메일·연락처를 기재한다. 자료에 없는 개인정보를 추정하지 않는다.
- 사진을 쓰는 양식이라면 단정한 헤어·복장에 본인을 분명히 식별할 수 있는 프로필 사진을 선택한다. 옆모습·뒷모습·단체사진보다 정면에서 확인하기 쉬운 사진을 권장한다.
- 오래된 졸업사진보다 최근 6개월 이내 프로필 사진을 권장하되 촬영일을 모르면 최근 사진이라고 쓰지 않는다. 사진은 필수가 아니며 블라인드 채용·개인정보 금지 지침을 우선한다.

## 슬로건·짧은 소개

- 직무에 필요한 강점·역량·기술을 짧게 소개하고, 경력·프로젝트에서 확인할 근거와 연결한다. 관련 가치관·태도를 포함할 수 있다.
- 짧은 서술식 소개와 핵심 역량 목록을 함께 구성한다. 추상적 자기평가를 반복하기보다 어떤 일을 할 수 있는지 보여 준다. 미확인 연차·숙련도를 추가하지 않는다.

## 경력사항

- 직무 관련 회사 경력·인턴·아르바이트·현장실습 등을 최근순으로 배치한다. 직무 관련성이 더 중요하면 순서를 조정하되 기간은 명확하게 표시한다.
- 회사·부서/직무·근무기간과 **담당업무 → 사용 기술 → 결과·성과**를 정리한다. 실제로 확인된 부서·직함만 사용한다.
- 담당업무는 대상·행동·범위가 드러나는 명사형으로 작성한다. 회사 아래 서비스·작업 단위를 구성하고 본문의 압축 기준을 적용한다.
- 기능 목록만으로 기여가 드러나지 않으면 설계 문서·코드·PR·사용자 설명을 확인한다. 직접 만든 구조와 기술적 판단이 드러나는 기여부터 배치한다.

## 프로젝트 이력

교육과정·팀·개인·토이 프로젝트 중 직무 관련 경험을 고르고 다음 순서로 간략히 정리한다.

| 항목 | 내용 |
|---|---|
| 개요 | 주제·목적, 확인된 기간, 팀/개인 여부와 확인된 팀 규모 |
| 역할/구현기능 | 본인이 맡은 역할, 구현한 기능·해결한 문제 |
| 사용 기술 | 해당 작업에 실제 사용한 언어·프레임워크·라이브러리·도구 |
| 결과/성과 | 완성·배포·사용·개선 결과와 확인된 정량 지표 |

회사 경력과 같은 맥락·압축 기준을 적용한다. 서비스 전체 기능 대신 본인 책임과 대표 기여를 보여 주고, 상세 설명은 실제로 존재하는 포트폴리오로 연결한다. 팀 규모와 기여율은 서로 다른 정보다.

## 학력

- 학교명·학과명, 재학·졸업·졸업예정 상태와 기간을 정확히 표시한다. 과거 문서의 졸업예정을 현재 상태로 단정하지 않는다.
- 고등학교 항목이 필요하면 학과 전공 대신 인문계·자연계·특성화계열 등 해당 계열을 기재한다.
- 기업 양식과 사용자 선택에 따라 확인된 학점·복수전공 등 부가정보를 포함한다.

## 기술·스킬

- 공고 관련 기술을 먼저 두고 실제 사용 경험과 활용 가능한 범위를 면접에서 설명할 수 있게 적는다. 근거 없는 상·중·하 평가나 이름 나열에만 의존하지 않는다.
- 기술별로 무엇을 구현했는지·어떤 기능을 사용할 수 있는지 짧게 보충한다. 프로젝트에 썼다는 사실이 해당 기술의 모든 기능에 숙련되었다는 뜻은 아니다.
- 언어·프레임워크·라이브러리·도구의 실제 이름을 범주별로 제시한다. 기능명이나 긴 업무 설명으로 기술 이름을 대체하지 않는다.

## 수상·자격증·교육·기타 활동

- 자격증·수상·교육·공모전·경진대회·동아리 등 직무 관련 경험을 `[자격증]`, `[교육사항]`처럼 유형별로 구분한다.
- 수상은 수상명·시기·활동 내용·본인 참여 역할, 확인된 주관기관을 적는다.
- 교육은 **교육과정명 → 교육기간 → 교육기관 → 교육내용** 순으로 정리하고 실제로 배운 내용과 습득·향상한 역량을 구체화한다.
- 외국어는 언어·시험명·응시/취득일·점수 또는 확인된 활용 수준을 구분한다. 자격의 현재 유효성은 확인 후 표시한다. 해외 경험의 배치는 사용자 선호 참조를 따른다.
- GitHub·블로그·포트폴리오 링크 확인은 공통 출력 기준을 따른다.

## 조건부 표현 예시

아래는 문체와 구체성의 예시다. 지원자의 사실이나 필수 기술 목록이 아니며, 해당 역할·조치·결과가 원자료에서 확인된 경우에만 사용한다.

- `문서작업`보다 `데이터 통계 기반의 월별 소비자 니즈 분석 관련 문서 작성`처럼 대상과 작업을 드러낸다.
- DB 기반 알림 디스패처와 재시도·중복 제어를 실제로 설계·구현했다면 `서비스 규모를 고려한 DB 기반 알림 디스패처 설계 및 발송 재시도와 중복 처리 제어 구현`처럼 쓸 수 있다.
- 기관별 API 데이터의 공통 형식 변환·통합 조회를 구현했다면, 어떤 정보가 흩어져 있었고 어디서 함께 확인하게 되었는지 쓴다. 기술명만 덧붙이지 않는다.
- Remotion의 단일 탭 전환과 특정 고부하 환경의 프레임 깨짐 해소가 확인되었다면 `Remotion을 단일 탭 렌더링으로 전환해 고부하 환경의 프레임 깨짐 해소`처럼 적을 수 있다. 공용 제작 모듈 분리도 했다면 이는 별도 기여로 나눈다. 다른 환경의 결과나 미확인 원인은 덧붙이지 않는다.
- MySQL로 테이블 생성·수정·관계 설정을 실제 수행했다면 해당 범위를 적는다. 단순 사용 이력으로 전 기능 숙련을 주장하지 않는다.
- `자연어처리 개발능력 강화` 같은 교육 결과도 해당 교육과 실제 경험에 근거할 때만 쓴다.

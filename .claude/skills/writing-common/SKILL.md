# writing-common

이력서와 개발자 포트폴리오에서 무엇을 사실로 쓸 수 있는지, 어떤 경험을 대표 사례로 고를지 판단한다. 개인 이력 데이터나 기업별 지원 맥락은 스킬에 저장하지 않고 제공된 원자료에서 확인한다.

## 작업 경계

- 사용자의 최신 명시적 지시, 기업 제출 규정, 프로젝트 지침을 우선한다. 이미 받은 정보는 다시 묻지 않는다.
- 원문 보존·분류, 문장 제안, 실제 파일 반영을 구분한다. 보존 요청에는 임의 재작성을 하지 않고, 제안 요청에는 파일을 바꾸지 않는다. 제출본 선별을 이유로 마스터 이력을 삭제하지 않는다.
- 요청한 문서와 매체만 다룬다. 링크가 있다는 이유로 다른 문서를 제작하거나 사이트 구현·외부 제출·게시로 작업을 확대하지 않는다.
- 전문 스킬이 이 공통 기준을 참조한다. 여기서 전문 스킬을 다시 읽도록 순환 호출하지 않는다. 전역 `developer-application-evidence`는 필요할 때 쓰는 보조 검토 역량이며 필수 의존성이 아니다.

## 사실·추정·확인 범위

- 회사·역할·기간·학력·기술·성과는 원자료에서 확인된 내용만 쓴다. 사용자 확정값은 적용하되, 상충하는 날짜·수치·직함은 임의로 선택하지 않고 미확정 목록에 남긴다. 과거의 졸업예정·자격 상태를 현재 사실로 바꾸지 않는다.
- 원문에서 확인된 사실, 해석·원인 가설, 아직 확인하지 못한 사항을 구분한다. 명백한 철자 오타는 작성본에서 고치되 식별자·고유명사·코드·날짜의 불일치를 오타로 단정하지 않는다.
- 원래 구현 범위와 추상화 수준을 유지한다. 여러 유형을 포괄하는 공통 구조를 임의의 두 유형만 지원하는 구조로 좁히거나, 일부 구현을 전체 지원으로 넓히지 않는다.
- 수치가 없으면 만들지 않는다. 측정값에는 환경·기간·비교 대상·측정 조건을 유지한다. 구현된 기능이나 테스트 통과만으로 운영 비용 절감·사용자 만족·장애 예방·확장성 향상을 단정하지 않는다.
- 팀 목표·팀 성과와 본인의 책임·판단·변경을 나눈다. 팀 인원으로 기여율을 계산하거나 커밋 수·테스트 건수를 성과로 치환하지 않는다. AI 사용 여부나 기능 구현이라는 이유만으로 기여를 낮추거나 높이지 않는다.
- 접근하지 못한 상세 페이지, 보지 못한 모바일 화면, 실행하지 않은 테스트는 미확인이다. 일부 환경에서의 결과를 운영 전체에 일반화하지 않는다. 여러 자료가 충돌하면 필요한 주장에 한해 `주장 | 출처·위치 | 실제 확인 범위 | 확정/추정/미확정`으로 기록한다. 단순 교정마다 별도 원장을 만들 필요는 없다.

## 대표 경험과 STAR 분석

직무 관련성, 본인 책임, 실제 판단과 변화가 드러나는 경험부터 고른다. 기능·기술 개수를 늘리기보다 다음 근거를 확인한다.

| 분석 요소 | 확인할 내용 |
|---|---|
| Situation — 상황 | 누구의 어떤 문제인지, 기존 구조·운영 조건·제약 |
| Task — 목표·책임 | 프로젝트 전체 목표와 구분되는 본인의 목표·책임 범위 |
| Action — 행동 | 본인이 판단하고 설계·구현·변경한 내용과 근거 있는 선택 이유 |
| Result — 결과 | 달라진 동작·구조, 확인한 효과와 검증 조건·한계 |

- STAR는 근거를 분석하는 틀이다. 최종 문서에 네 칸·라벨·동일한 소제목을 강제하지 않으며, 단순 기능마다 문제와 성과를 만들어 붙이지 않는다.
- 설계 선택은 실제 서비스 규모·트래픽·운영 부담·개발 제약에 맞춰 설명한다. 단순한 구성도 유효한 선택이다. 검토하지 않은 대안이나 쓰지 않은 대규모 인프라를 추가하지 않는다.
- 기술명보다 무엇을 어떤 경계로 분리했고, 어떤 데이터를 연결했으며, 어떤 불필요한 작업을 줄였는지 확인한다. 아키텍처 명칭은 실제 구조가 뒷받침할 때 쓴다. 모듈화·동시성·성능 병목·외부 라이브러리 제약은 확인 질문의 예시이며, 용어만으로 난도를 인정하지 않는다.
- 오류 수정은 발생 조건, 본인 판단, 실제 조치, 확인된 변화를 보고 대표 사례 여부를 정한다. 단순 오타·누락·설정 실수 정정을 기술적 성과로 포장하지 않는다. 조치가 한 줄이어도 판단과 효과가 확인되면 유효한 사례다.
- 해결 방식이나 기여가 불명확하면 추가 확인하거나 대표 사례에서 보류한다. 보존 요청을 받은 마스터 기록은 유지한다. 해결·인과·운영 효과를 추정하여 빈칸을 채우지 않는다.

## 참고 사례와 예시의 경계

- 참고 자료에서는 문장의 구체성·정보 배치·증거 설명 방식을 배운다. 다른 사람의 이름·회사·연차·수치·기여율·설계 의도를 지원자의 이력으로 가져오지 않는다.
- 기술·문체 예시는 실제 조치와 결과가 확인된 경우에만 적용한다. 예시 자체를 개인 이력의 근거로 사용하지 않는다.
- 비교 검토를 요청받으면 정보 전달 디자인과 문제 해결 내용의 평가를 구분하고 관찰 범위를 남긴다. 미열람을 낮은 품질로 판정하거나 참고 점수를 합격 확률로 해석하지 않는다. 일상적인 수정마다 조사·점수표·병렬 검토를 강제하지 않는다.

## 출력과 전달

파일 저장·분량·링크·HTML·PDF를 실제로 확인할 때는 [출력 확인 기준](references/output-checks.md)의 해당 매체 항목만 읽는다. 완성본 또는 요청 파일을 먼저 전달하고, 필요한 미확정 정보와 실제 검증·미검증 범위를 짧게 알린다. 제안만 한 내용이나 열어 보지 않은 출력물을 완료했다고 보고하지 않는다.

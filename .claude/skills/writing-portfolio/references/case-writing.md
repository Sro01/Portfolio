# 사례 편집과 증거 설명

프로젝트 상세를 쓰거나 그 상세의 증거 배치를 검토할 때 사용한다. 사실 판정은 공통 스킬이 소유하며, 여기서는 확인된 근거를 독자가 따라갈 수 있게 편집한다.

## 사례의 읽기 흐름

- 첫 부분에서 프로젝트 목적·본인 역할·핵심 변경과 확인된 결과를 짧게 제시한다. 팀 전체 서비스 소개와 개인 기여가 한 문장에 섞이지 않게 한다.
- 변경을 이해하는 데 필요한 기존 구조와 제약을 설명한 뒤, 본인의 판단이 실제 변경과 어떻게 연결되는지 보여 준다. 모든 기능에 기술적 난점을 붙일 필요는 없다.
- `모듈화`라면 나눈 책임과 의존 방향, `통합`이라면 원천 데이터와 공통 형식·조회 경로, `성능 개선`이라면 줄인 작업과 측정 범위처럼 주장에 해당하는 실제 변경을 드러낸다. 해당 작업을 했다는 근거가 있을 때만 적용하는 설명 관점이다.
- 선택한 구성의 장점뿐 아니라 당시 제약과 남은 한계를 연결한다. 기록에 없는 대안 비교·트레이드오프·원인 분석을 사후에 지어내지 않는다. 향후 개선안은 현재 구현과 분리해 계획으로 표시한다.
- 결론을 이해하는 데 필요한 재현·실험만 남긴다. 시행착오를 전부 나열하지 않되, 증거가 제한적인 결론을 확정 사실로 압축하지 않는다.

## 증거의 역할

| 증거 | 설명할 내용과 확인 한계 |
|---|---|
| 코드·PR·커밋 | 관련 위치와 실제 바뀐 책임·동작. 링크만으로 본인 소유·설계 의도·운영 효과까지 입증하지 않는다 |
| 화면·동작 기록 | 사용자가 할 수 있는 일과 확인한 상태·환경. 화면만으로 내부 구조·성능·안정성을 증명하지 않는다 |
| 구조·흐름 도식 | 실제 코드·문서와 대응하는 경계·데이터 흐름. 구상도라면 현재 구현과 구분한다 |
| 테스트·재현 결과 | 확인한 조건·기대 동작·실행 결과와 미확인 조건. 테스트 수를 사업 성과로 바꾸지 않는다 |
| 측정 자료 | 지표의 정의, 전후 비교 대상·환경·기간과 실제 측정값. 다른 환경·기간의 운영 전체로 확대하지 않는다 |

- 증거 링크는 저장소 루트 대신 관련 README·파일·PR·커밋으로 연결하고, 그 링크로 무엇을 판단할 수 있는지 한 줄로 붙인다.
- 회사의 비공개 저장소나 내부 자료는 증거로 공개하지 않는다. 공개할 수 없는 실무는 설명과 확인 가능한 범위로 대신한다.
- 실행·로그인·외부 이동 없이도 핵심을 이해할 수 있게 한다. 데모는 중요한 장면을 먼저 보여 주고 코드·문서는 더 깊이 볼 경로로 둔다.
- 최신 기술 이름이나 패턴을 적용했다는 사실 자체를 강점으로 내세우지 않는다. 수정하기 쉬운 구조, 제품 완성도, 읽기 쉬운 PR·커밋, 설명이 있는 README처럼 판단할 수 있는 근거를 보여 준다.
- 팀 프로젝트는 인터페이스 합의·리뷰·조율 같은 실제 협업 행동을 구체적으로 쓴다. 외부 라이브러리나 기존 코드를 활용한 부분을 독창적인 작업처럼 쓰지 않는다.

핵심 주장 곁에 증거와 짧은 해설을 두고, 전체 자료는 필요할 때 더 볼 수 있게 연결한다. 증거마다 긴 해설이나 모든 종류의 증거를 의무로 붙이지 않는다. 자료가 구현 사실까지만 보여 주면 주장도 그 범위로 맞춘다.

## 요약·상세·이력서 대조

- 목록의 요약이 상세에서 실제로 뒷받침되는지 확인한다. 제목만 과장되거나 사례마다 같은 소개·기술 목록이 반복되면 핵심 주장 중심으로 정리한다.
- 이력서가 제공되면 같은 프로젝트의 명칭·기간·역할·기술·결과를 대조한다. 표현의 길이는 달라도 사실과 확인 범위는 같아야 한다. 개인 역할을 확인하지 못한 팀 기록은 그 한계를 유지한다.
- 근거가 부족한 내용은 제출 본문에서 확정 사실처럼 쓰지 않고 확인 필요 사항으로 분리한다. 기록 보존 요청이 있다면 원자료는 유지하면서 대표 사례 채택만 보류할 수 있다.
- 전달 구조·가독성을 검토한 범위와 기술 내용·증거를 검토한 범위를 각각 남긴다. 상세나 모바일을 열지 못한 경우 해당 범위는 미확인으로 기록한다.

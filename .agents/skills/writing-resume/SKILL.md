# writing-resume

제공된 이력을 지원 직무와 연결하고, 담당 역할·사용 기술·결과를 빠르게 읽을 수 있는 한국어 이력서로 작성한다. 사용자와의 대화는 존댓말로 한다.

## 기준과 적용 범위

전체 이력을 정리하는 마스터 이력서와 특정 기업·직무에 맞춘 제출용 이력서의 작성·검토에 적용한다. 사용자의 명시적 지시와 지원 기업의 제출 규정을 우선하며, 아래 권장사항은 제출 조건에 맞게 적용한다.

## 시작할 때

1. 요청이 전체 이력을 보관하는 **마스터**, 특정 공고의 **제출본**, 기존 문서의 **검토·수정** 중 무엇인지 파악한다.
2. 제공된 기업명·직무명·공고, 자유양식/기업 지정 양식, 원본 이력·프로젝트 자료, 제출 파일 형식·분량 제한을 확인한다. 이미 주어진 내용은 다시 묻지 않는다.
3. 작성에 영향을 주는 정보가 없으면 필요한 것만 질문한다. 목표 공고가 없더라도 일반 마스터 정리는 진행할 수 있다.
4. 원문과 작성 결과를 구분한다. 원문 보존만 요청받았다면 분류·배치에 집중하고 문장 재작성은 해당 요청 범위에 맞춘다.
5. 제안 요청과 파일 반영 요청을 구분한다. 제안만 요청받으면 파일을 변경하지 않으며, 반영 요청을 받으면 최신 합의안을 적용하고 실제 저장 결과를 확인한다. 나중에 정정된 선호가 이전 선호보다 우선한다.

### 사실 보존

- 회사명·직무·기간·학력·기술·성과는 제공 자료에서 확인된 것만 사용한다. 예시 이력의 이름·회사·연차·기여율·성과 수치를 지원자의 정보로 가져오지 않는다.
- 숫자가 없으면 측정값을 만들지 않는다. 확인된 구현 결과를 정성적으로 쓰고, 추가로 확인하면 좋은 지표는 본문 밖에 적는다.
- 팀의 성과와 본인의 역할을 구분한다. 팀 전체 작업을 단독 개발로, 커밋 수를 성과나 기여율로 바꾸지 않는다.
- 상충하는 날짜·수치·직함은 임의로 선택하지 않는다. 사용자 확정값이 있으면 적용하고, 미확정 사항은 별도 목록에 남긴다.
- 명백한 철자 오타는 작성본에서 수정한다. 식별자·고유명사·코드·날짜의 불일치는 오타라고 단정하지 않는다.
- 구현 범위와 추상화 수준을 보존한다. 예를 들어 취미 기록 전반의 공통 구조를 특정 취미 두 개의 공통 구조로 축소하지 않는다. 확인된 조치·결과와 추정한 원인을 구분하고, 원인 추론을 확정된 사실로 쓰지 않는다.

## 항목별 작성 기준

### 지원분야·제목

- 기업명과 직무명을 명확하게 표시한다.
- 제목에 `기업명 직무명 지원_이름`을 쓰거나, 이름 아래 `지원기업: … / 지원직무: …`를 둔다. 둘 다 반복할 필요는 없다.
- 마스터에는 기업별 정보가 확정되어 있지 않아도 된다. 제출본을 만들 때 해당 공고의 실제 명칭을 적용한다.

### 사진·인적사항

- 채용 연락을 받을 정확한 이메일과 연락처를 기재한다. 자료에 없는 개인정보는 추정하지 않는다.
- 사진을 사용하는 양식이라면 단정한 헤어·복장과 신뢰감 있는 프로필 사진을 선택한다. 옆모습·뒷모습·단체사진보다 본인을 분명하게 식별할 수 있는 사진을 사용한다.
- 오래된 졸업사진보다 최근 6개월 이내에 촬영한 프로필 사진을 권장한다. 사진 촬영일이 확인되지 않으면 최근 사진이라고 쓰지 않는다.
- 사진은 항상 필수가 아니다. 블라인드 채용 또는 사진·개인정보 기재 금지 지침이 있으면 해당 지침에 따른다.

### 슬로건·짧은 소개

- 지원 직무에 대한 강점·역량·기술을 짧게 소개한다. 직무 관련 가치관·태도를 포함할 수 있다.
- 짧은 서술식 소개와 핵심 역량 목록을 혼합한다. 경력·프로젝트에서 확인할 수 있는 근거와 연결한다.
- 추상적인 자기평가를 반복하기보다 어떤 일을 할 수 있는지 드러낸다. 확인되지 않은 연차나 숙련도를 넣지 않는다.

### 경력사항

- 직무와 관련된 회사 경력·인턴·아르바이트·현장실습 등을 포함한다.
- 기본적으로 최근 경력부터 배치한다. 직무 관련성이 더 중요한 경우 우선순위를 조정하고, 각 항목의 기간은 분명하게 표시한다.
- 회사·부서/직무·근무기간과 함께 **담당업무 → 사용 기술 → 결과·성과**를 정리한다.
- 담당업무는 대상·행동·범위가 드러나도록 구체화하고 명사형으로 마무리한다.
- 담당업무 표현 예: `문서작업`보다 `데이터 통계 기반의 월별 소비자 니즈 분석 관련 문서 작성`. 이는 문체 예시이며 실제 경력으로 추가하지 않는다.
- 성과는 근거가 있을 때 수치화한다. 비교 기준·측정 조건이 있는 수치는 그 의미를 유지한다.

### 프로젝트 맥락과 STAR 기반 경험 서술

- 회사 아래에 서비스 또는 주요 작업 단위를 배치하고, **어떤 서비스를 위한 작업인지 → 본인의 역할과 책임 → 구체적인 기여** 순서로 이해할 수 있게 구성한다. 프로젝트별 기간은 확인된 자료가 있을 때만 별도로 표시하며 회사 근무기간을 임의로 나누지 않는다.
- 제목은 `서비스명 + 서비스 설명` 또는 `대상 + 수행한 작업`으로 작성한다. 내부 서비스명만 적지 말고, 대상 사용자와 목적 또는 이번에 맡은 작업 범위를 드러낸다. 예: `투약·건강 기록 관리 미니앱 개발`, `음성 인터뷰 기반 영상 제작 서비스 개발`. 서비스명은 필요할 때 보조적으로 병기한다.
- 같은 프로젝트의 맥락이 이어지도록 관련 작업을 묶는다. 소제목이 필요하면 `정보 수집·조회 통합`, `영상 제작 안정화`처럼 실제 작업 단위를 사용한다. 사용자가 업무 성격별 분류를 요청하면 그 형식을 따르되, `설계/개발/개선` 범주에 같은 경험을 흩어 놓거나 모든 불렛에 개별 소제목을 붙이지 않는다.
- 핵심 경험은 정리된 자료·설계 문서·코드·PR·커밋·사용자 설명을 바탕으로 아래 STAR 요소를 확인한다. 기술적 판단, 문제 해결, 본인의 책임이 드러나는 경험부터 선별하며, 모든 기능을 STAR 사례로 늘려 쓰지 않는다.

| 요소 | 작성 전 확인할 근거 |
|---|---|
| Situation — 상황 | 사용자 문제, 기존 구조의 한계, 운영 조건이나 제약 |
| Task — 목표·책임 | 해당 상황에서 본인이 맡은 목표와 책임 범위. 프로젝트 전체 목표와 구분 |
| Action — 행동 | 본인이 판단하고 설계·구현·변경한 구체적인 내용 |
| Result — 결과 | 그 조치로 달라진 동작이나 구조, 확인된 효과와 측정 조건 |

- STAR는 경험을 분석하는 틀이며 최종 출력의 네 칸짜리 양식이 아니다. 불렛마다 S/T/A/R 라벨을 붙이거나 네 요소를 모두 길게 서술하지 않는다. 프로젝트 설명에서 전달한 상황·목표는 반복하지 않고, 본인의 구체적인 행동과 확인된 결과를 중심으로 압축한다.
- 최종 문장은 **무엇을 위해 어떤 작업을 했으며 무엇이 달라졌는지** 이해할 수 있어야 한다. `통합`, `연동`, `구조 설계`로만 끝내지 말고, 어떤 데이터를 어떤 방식으로 연결했는지 또는 사용자가 무엇을 할 수 있게 되었는지 설명한다. 기술명은 해결 방식을 설명하는 데 필요한 만큼 사용한다.
- 조사·재현·실험을 시간순으로 서술하지 않는다. 본인의 책임과 최종 해결을 드러내는 핵심 맥락만 남기고, 상세한 판단 과정은 포트폴리오·면접용 근거로 분리한다.
- 결과는 수치뿐 아니라 통합 조회, 중복 처리 제어, 중단 작업 복구처럼 확인 가능한 변화로도 표현한다. 수치가 있으면 환경과 비교 기준을 유지한다. 구현 사실만으로 운영 비용 절감·사용자 만족도 향상·장애 예방을 단정하지 않는다. 결과 근거가 부족하면 확인된 구현 범위까지만 적고, 참고 사례의 수치나 성과를 가져오지 않는다.
- 단순 기능도 담당 범위를 설명하는 데 필요하면 간결하게 유지한다. 모든 항목에 문제나 성과를 만들어 붙이지 않으며, 오류 수정의 대표 사례 채택 여부는 아래 선별 기준을 따른다.

### 개발 경력의 경쟁력 고도화

- 경력 불렛은 **본인이 무엇을 설계·구현·개선했는지**를 중심으로 한 문장씩 작성한다. 화면 폭에 맞추려고 글자를 줄이거나 강제 한 줄 처리를 하지 않는다.
- 경력 안에서는 지원 직무와 관련 있고 본인의 기여가 구체적으로 드러나는 사례를 먼저 배치한다. 기능 수나 사용 기술 수를 늘리기보다 직접 만든 구조, 기술적 판단이 드러나는 문제 해결, 개선한 처리 흐름을 대표 사례로 고른다. 서비스 개요와 팀 전체 성과는 본인의 작업과 구분한다.
- 기능 목록에서 기여의 깊이가 드러나지 않으면 설계 문서·코드·PR·사용자 설명을 확인한다. 서비스 규모에 맞춘 구성, 외부 데이터의 공통 모델 통합, 모듈 경계·의존성 분리, 동시성 제어, 성능 병목 개선 등 실제 판단이 드러나는 사례를 골라 보완한다.
- 선택 이유가 설명력을 높이는 불렛에는 `서비스 규모를 고려한 …`처럼 짧게 담는다. 모든 문장에 문제·이유·대안·성과를 형식적으로 넣지 않으며, 상세한 의사결정 과정은 포트폴리오·면접용 근거로 분리한다.
- 설계 선택은 실제 트래픽·서비스 규모·운영 부담·개발 제약에 맞춰 설명한다. 단순한 구성의 선택도 유효한 판단으로 다루며, 사용하지 않은 대규모 인프라나 검토하지 않은 대안을 덧붙여 복잡한 설계처럼 포장하지 않는다.
- `클린 아키텍처 적용`, `모듈화`, `성능 최적화`만으로 끝내지 않는다. 무엇을 어떤 경계로 분리했는지, 어떤 데이터를 공통화했는지, 어떤 불필요한 작업을 줄였는지 구체적으로 적는다. 아키텍처 이름은 실제 구조가 뒷받침할 때 쓴다.
- 운영·성능 개선은 확인한 원인과 변경 지점을 연결한다. 예를 들어 막연한 `성능 최적화`보다 `진행 상태 갱신을 카드 렌더링에서 분리`처럼 실제 조치를 적고, 측정값이 있으면 환경·비교 범위를 유지한다.
- 모든 불렛에 정량 성과가 필요한 것은 아니다. 수치가 없으면 중복 처리 방지, 실패 작업 복구, 분산된 데이터의 통합 조회처럼 확인 가능한 동작·구조의 변화로 기여를 설명한다. 구현한 기능을 운영 효과로 바꾸거나, 테스트 건수·커밋 수를 사업 성과로 대신하지 않는다.
- 기능 구현 자체를 낮게 평가하거나 AI 사용 여부로 기여를 판단하지 않는다. AI 도구 이름보다 본인의 설계·검증·개선 범위를 드러내고, 확인되지 않은 비용 절감·확장성·유지보수성 향상을 성과로 만들지 않는다.
- 레퍼런스는 문장의 구체성과 정보 배치를 참고하는 데 사용한다. 다른 지원자의 수치·성과·설계 의도를 가져오지 않는다. 조사나 병렬 검토는 요청 범위와 필요에 따라 수행하며 일상적인 문장 수정마다 강제하지 않는다.
- 하나의 불렛에는 하나의 핵심 기여를 담는다. 공용 모듈 분리와 렌더링 문제 해결처럼 독립적인 기여는 분리하되, 하나의 해결 방식과 그 결과는 함께 유지한다. 기능마다 잘라 불렛 수만 늘리지 않는다.

표현 예시(해당 사실이 확인된 경우에만 사용):

- `푸시 알림 구현` → `서비스 규모를 고려한 DB 기반 알림 디스패처 설계 및 발송 재시도와 중복 처리 제어 구현`
- `공공 서비스 데이터 수집` → `여러 공공기관에 흩어진 교육/문화/복지/일자리 정보를 한곳에서 확인할 수 있도록 기관별 API 데이터를 공통 형식으로 변환하고 통합 조회 구조 설계`

### 오류 수정 경험의 선별과 기술적 해결 서술

- 오류 수정은 정상 동작을 완성하기 위한 기본 작업일 수 있다. 수정했다는 사실만으로 대표 성과에 넣지 말고, 본인이 해결한 기술적 난점과 판단이 드러나는 사례인지 먼저 판단한다. 단순 오타·누락·설정 실수의 정정을 기술적 성과로 포장하지 않는다.
- 정리된 자료·설계 문서·코드·PR·커밋·사용자 설명에서 문제의 발생 조건, 실제 변경 방식, 확인된 결과와 본인의 기여를 확인한다. 동시성·자원 경쟁·성능 병목·외부 라이브러리 제약 등은 판단에 도움이 되는 예시이며, 용어가 등장한다는 이유만으로 기술적 난점으로 인정하지 않는다.
- 기술적 문제 해결로 선별한 불렛은 **최종적으로 어떤 문제를 어떻게 해결했는지** 드러내도록 작성한다. `오류 수정`, `렌더링 깨짐 해결`만으로 끝내지 않으며, 실제 조치와 해결된 문제를 연결한다. 조치가 설정 한 줄이어도 근거 있는 기술적 판단과 효과가 확인되면 유효한 사례다.
- 조사·재현·가설·실험·검증을 시간순으로 나열하지 않는다. 이 과정은 포트폴리오나 면접용 근거로 보관하고, 이력서에는 최종 해결 방식과 확인된 결과를 압축한다. 근거가 특정 환경에 한정되면 그 범위를 유지한다.
- 자료에 해결 방식이나 기여가 없으면 추가 확인하거나 대표 성과 후보에서 제외한다. 사용자가 보존을 요청한 마스터 기록은 유지하되, 기술적 난점·원인·성과를 추정해 보충하지 않는다.

표현 예시(해당 조치와 결과가 확인된 경우에만 사용):

- `렌더링 깨짐 오류 수정` → `Remotion을 단일 탭 렌더링으로 전환해 고부하 환경의 프레임 깨짐 해소`
- 공용 제작 모듈 분리와 위 렌더링 개선은 독립된 불렛으로 작성한다. 조사나 검증 절차를 추가해 문장을 길게 만들지 않는다.

### 프로젝트 이력

- 교육과정·팀·토이·개인 프로젝트 중 지원 직무와 관련된 경험을 선택한다.
- 각 항목을 **개요 → 역할/구현기능 → 사용 기술 → 결과/성과** 순으로 구성한다.

| 항목 | 포함할 내용 |
|---|---|
| 개요 | 프로젝트 주제·목적, 기간, 팀/개인 여부. 인원이 확인되면 팀 규모 |
| 역할/구현기능 | 본인이 맡은 역할과 실제 구현한 기능·해결한 문제 |
| 사용 기술 | 해당 작업에 실제로 사용한 언어·프레임워크·도구 |
| 결과/성과 | 완성·배포·사용·개선 결과. 확인된 정량 지표가 있으면 함께 표시 |

- 이력서에서는 핵심을 간략히 제시하고 상세 설명은 포트폴리오로 연결한다. 요청하지 않은 포트폴리오 제작까지 작업을 확대하지 않는다.
- 회사 경력과 마찬가지로 위의 프로젝트 맥락과 STAR 기준을 적용한다. 서비스 전체 기능을 나열하기보다 본인이 맡은 책임과 대표적인 설계·구현·문제 해결 경험을 보여준다.
- 팀 인원과 기여율은 서로 다른 정보다. 팀 규모로 기여율을 계산하지 않는다.

### 학력

- 학교명·학과명을 정확히 쓰고 재학·졸업·졸업예정 상태와 기간을 표시한다.
- 고등학교 항목이 필요하면 학과 전공 대신 인문계·자연계·특성화계열 등 해당 계열을 기재한다.
- 기업 양식과 사용자의 선택에 따라 학점·복수전공 등 확인된 부가정보를 포함한다. 과거 문서의 졸업예정을 현재 사실로 단정하지 않는다.

### 기술·스킬

- 지원 공고와 관련된 기술을 먼저 배치한다. 실제 사용 경험과 활용 가능한 범위를 설명한다.
- 면접에서 설명할 수 있는 수준으로 작성한다. 기술 이름 나열이나 근거 없는 상·중·하 평가에만 의존하지 않는다.
- 기술별로 `무엇을 구현했는지 / 어떤 기능을 활용할 수 있는지`를 쓴다. 예: MySQL을 실제로 다뤘다면 테이블 생성·수정·관계 설정 등 확인된 범위를 명시한다.
- 프레임워크와 도구를 프로젝트에서 사용했다는 사실이 모든 기능의 숙련을 의미하지는 않는다.
- 기술 스택은 실제 언어·프레임워크·라이브러리·도구 이름을 범주별로 제시하고 활용 경험은 짧게 보충한다. `AI 스트리밍 채팅` 같은 기능명이나 긴 업무 설명으로 기술 이름을 대체하지 않는다.

### 수상·자격증·교육·기타 활동

- 자격증·수상내역·교육·공모전·경진대회·동아리 등 직무 관련 자료를 정리한다. `[자격증]`, `[교육사항]`처럼 유형을 구분해 읽기 쉽게 한다.
- 수상은 수상명·시기·어떤 활동인지·본인의 참여 역할을 적는다. 확인된 주관기관 정보가 있으면 포함한다.
- 교육은 **교육과정명 → 교육기간 → 교육기관 → 교육내용** 순으로 정리한다. 무엇을 배웠고 어떤 역량을 습득·향상했는지 구체화한다.
- 예시의 ‘자연어처리 개발능력 강화’ 같은 결과는 해당 교육과 실제 경험에 근거할 때만 쓴다.
- 외국어는 언어·시험명·응시/취득일·점수 또는 확인된 활용 수준을 구분한다. 자격의 유효성을 확인하지 않고 유효하다고 단정하지 않는다.
- GitHub·블로그·포트폴리오 링크는 실제 주소와 대상을 확인하여 연결한다. 접근 여부를 확인하지 못한 링크는 검증 완료로 보고하지 않는다.

## 분량·문체·양식

- **마스터:** 활용 가능한 이력을 충분히 보관한다. 분량을 줄이기 위해 원본 경력을 삭제하지 않는다.
- **제출본:** 최대 2페이지 이내를 권장하되, 공고의 분량 규정을 우선한다. 한 페이지에 과도하게 압축하지 말고 가독성과 직관성을 우선한다.
- 정보 밀도를 우선한다. 같은 PWA 판별 작업이나 SDK 협업을 표현만 바꿔 여러 불렛에 반복하지 않고, 글자 수를 채우기 위한 기술 용어 풀이를 넣지 않는다. 분량을 늘려야 한다면 근거가 있는 다른 책임·판단·결과를 보충한다.
- 글자 수 상한과 정확한 글자 수 요구를 구분하고, 회사별 제한이면 각 본문을 따로 계산한다. 소제목·공백·줄바꿈·불렛 표기의 포함 범위를 밝히고 최종 전달본을 계산한다. 분량 요구가 있어도 이력이나 효과를 지어내지 않는다.
- 경력·프로젝트의 세부 항목은 개조식·명사형으로 통일한다. 소개글에는 짧은 서술식을 허용한다.
- 날짜 표시는 기본 `YYYY.MM`로 통일한다. 일자까지 요구하는 항목은 `YYYY.MM.DD`를 사용하되, 알려지지 않은 일자를 만들어 채우지 않는다.
- 같은 목록 안에서는 날짜를 최근순으로 정리한다. 직무 중요도로 순서를 조정한 경우에도 기간을 일관되게 표시한다.
- **자유양식:** 이력과 직무에 맞게 항목을 추가·삭제할 수 있다.
- **기업 지정 양식:** 항목을 임의로 삭제하지 않는다. 빈 행 추가·삭제도 서식과 제출 안내에서 허용하는 범위 안에서 수행한다. 해당하지 않는 항목은 지정된 표기 방법을 따른다.

## 현재 사용자의 편집·표기 선호

이 절은 이 사용자의 자유양식 이력서에 적용하는 기본 선호다. 모든 지원자의 보편 규칙으로 일반화하지 않으며, 최신 사용자 지시와 기업 지정 양식을 우선한다.

### 불렛 본문

- 개조식 항목의 끝 마침표는 생략한다. 서로 다른 문장의 마침표만 지워 붙이지 말고, 독립적인 기여는 별도 불렛으로 나누거나 문장을 자연스럽게 다시 쓴다. 소개글 등 서술형 문장까지 일괄 적용하지 않는다.
- 기능·범주를 나열하는 같은 묶음에서 항목이 2~3개면 쉼표, 4개 이상이면 `/`를 사용한다. 예: `접수, 재시도, 작업 복구`, `교육/문화/복지/일자리`. 한 문장 전체의 쉼표 개수로 판단하지 않는다.
- 기호로 연결할 필요가 없으면 `와`, `과`, `및`을 사용한다. 함께 사용하는 기술이나 인과관계를 기계적으로 쉼표나 `/`로 치환하지 않는다.
- 이 기호 정리 기준은 불렛 본문에만 적용한다. 제목·메타 정보·기술 스택·일반 설명까지 일괄 변경하지 않으며, 본문 밖 구분용 `·`는 허용한다. 기술명·날짜·학점·URL에 포함된 점과 슬래시는 보존한다.

### 경력 표기와 정보 배치

- 회사명 아래는 한국어 `직무 · 근무 형태`로 간결하게 적는다. `담당 영역` 라벨이나 별도 역할 설명을 덧붙이지 않는다. 원격근무가 확인된 경우 `계약직(원격근무)`처럼 표시할 수 있다. 실제로 없는 팀·부서·직급을 만들지 않는다.
- 교환학생은 `해외 경험`으로 분리하고 해당 경험과 영어 활용 수준을 함께 배치한다. 영어 하나 때문에 기술 목록에 독립 행을 추가하거나 협업 항목의 범위를 억지로 넓히지 않는다. 언어 활용 수준은 확인된 범위만 기재한다.
- 경력·프로젝트 아래 기술 스택은 인라인 코드 형식으로 표시한다. CSS 원형 구분자를 추가하지 않는다. 기술 섹션 전체의 분류나 기존 태그까지 변경하는 것으로 확대하지 않는다.
- 제안했던 분류안은 사용자가 확정하기 전까지 기본 규칙으로 저장하지 않는다. 회사별 직무·고용 형태 같은 개인 이력 사실은 원본 이력 자료에서 확인하며 스킬 예시를 실제 이력으로 사용하지 않는다.

### HTML 출력에만 적용하는 선호

- 목차가 있는 HTML 이력서는 새로고침 시 목차 앵커 주소를 초기화하고 직전에 보던 스크롤 위치를 유지한다. 목차를 눌렀을 때의 이동은 정상 작동해야 한다. 문장 수정마다 이 동작을 다시 구현하거나 일반 문서에 적용하지 않는다.

## PDF 출력이 요청된 경우

- PDF 내보내기 결과에 간격이 과도하게 벌어지거나 페이지가 잘리는지 확인한다.
- 간격이나 페이지 나눔을 조정해야 한다면 **전체 너비 조정 → HTML 내보내기 → 브라우저 인쇄 → 페이지 여백 조정**을 사용할 수 있다. 현재 도구와 사용자가 원하는 출력 방식에 맞춰 선택한다.
- PDF를 실제로 열어 줄바꿈·페이지 나눔·표 잘림·글꼴·링크를 확인한다. 작은 글씨로 억지로 페이지 수를 줄이지 않는다.
- Markdown만 작성했거나 출력물을 확인하지 못했다면 PDF 분량·레이아웃 검증을 완료했다고 말하지 않는다.

- [ ] 서비스명과 내부 용어를 몰라도 대상 사용자, 서비스 목적, 맡은 작업을 이해할 수 있는가?
- [ ] 핵심 경험의 상황·목표·행동·결과 근거를 확인하고, 프로젝트 전체 목표와 본인의 책임을 구분했는가?

- [ ] 경력이 기능·기술 이름 나열에 머물지 않고, 대표 사례의 실제 설계·개선 내용이 드러나는가?
- [ ] 불렛마다 이유·수치를 억지로 넣지 않았으며, 정성적 결과도 확인 가능한 변화로 표현했는가?
- [ ] 오류 수정 사례를 단순 정정과 기술적 문제 해결로 구분하고, 선별한 불렛에 어떤 문제를 어떻게 해결했는지 드러냈는가?
- [ ] 조사·실험 순서 대신 최종 조치와 결과를 담고, 추정 원인이나 검증 범위를 과장하지 않았는가?
- [ ] 독립적인 기여는 분리하고, 하나의 해결 방식과 결과는 함께 유지했는가?
- [ ] 기간·수치·졸업 상태에 근거가 있고 충돌한 정보가 임의로 확정되지 않았는가?
- [ ] 폰트·본문 크기·제목 단계가 일관적인가?
- [ ] 정렬·배열·여백이 맞고 빠르게 훑어볼 수 있는가?
- [ ] 날짜 형식이 일관되고 목록의 정렬 기준이 분명한가?
- [ ] 담당업무·프로젝트 항목이 개조식·명사형으로 정리되었는가?
- [ ] 불렛의 각 나열 묶음에 쉼표와 `/` 기준을 적용하고, 요청 범위 밖의 표기와 사실을 보존했는가?
- [ ] 회사명 아래 표기와 기술 스택 형식이 사용자의 최신 선호와 일치하는가?
- [ ] 제출 양식의 필수 항목과 분량 규정을 지켰는가?
- [ ] 동일한 기여를 반복하거나 글자 수를 채우기 위한 설명을 넣지 않았으며, 요구된 글자 수를 최종 본문에서 확인했는가?
- [ ] 철자·회사명·기술명·링크를 확인했는가?
- [ ] 요청된 출력 파일을 실제로 저장했는가? PDF라면 최종 출력물도 확인했는가?
- [ ] 반영 요청을 받은 최신 수정안이 실제 파일에 저장되어 있으며, 제안에만 머문 내용을 완료했다고 보고하지 않았는가?

## 결과 전달

완성된 작성본 또는 요청한 파일을 먼저 제공한다. 그다음 실제 확인이 필요한 날짜·성과·개인정보 등만 간단히 적는다. 미확정 정보는 제출용 본문에 확정 사실처럼 넣지 않는다. 기존 원문을 보존하면서 주요 수정 사항과 출력 검증 여부를 짧게 알린다. 작성·검토 요청만으로 외부 제출이나 게시를 수행하지 않는다.
